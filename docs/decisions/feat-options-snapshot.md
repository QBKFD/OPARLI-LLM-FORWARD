# feat/options-snapshot

The daily OG options snapshot: `backend/options/`, `deploy/options/`,
`tests/options/`. The owner asked for it on 2026-10-22, after the GEX
feasibility probe (PR #38), so that a GEX level test has a daily open-interest
history. This branch is stacked on `research/gex-feasibility`, so merge it
after PR #38. These are the decisions I took without the owner, each with its
alternative.

| # | Decision | Conservative because | Alternative |
|---|---|---|---|
| OS1 | **The probe's IBKR code moved to `backend/options/chain.py`, unchanged**: market hours, holidays, `Recorder`, chain discovery month by month, live-then-frozen batches, cancel-all. `tools/options_probe.py` now imports it and keeps only its JSON document, the daily bars and the CLI. `research/gex_feasibility/` is untouched, and its 68 tests pass unchanged. On the fake client, the old probe (`343e03f`) and the new one gave **byte-identical JSON, the same subscriptions, cancels and data-type requests**, in 5 cases (full run, frozen + silent contracts, 2-expiry fallback, errors 10197 and 101). Two differences: the 10197 message now says "run again" instead of "run the probe again"; and a variable in `run()` that was shadowed (`found`, reused for an underlying lookup) is now separate. That only mattered if an underlying wasn't in the futures list, which hasn't happened. | One implementation of what ran on 2026-10-22; behaviour checked, not assumed. | A copy of the probe code in `backend/` (two copies drift); import the probe by path (`tools/` isn't in any image). |
| OS2 | **The probe is no longer one self-contained file.** It needs `backend/options` next to it, so the stdin trick into the scanner image no longer works. It now runs from stdin in the options image (its docstring has the command), or as a script from the repo. The file exactly as it ran is `git show 343e03f:tools/options_probe.py`. | The study's record stays exact in git, and the live file has one source of truth. | Keep the probe frozen, and leave chain.py as a duplicate. |
| OS3 | **Same selection as the study:** the next 3 OG expiries at least 2 calendar days away, falling back to 2 (recorded). Monthly OG only (no weeklies). | Day-to-day data comparable with the study's R. | Include an expiry within 2 days (its gamma dominates on its last days), or the weeklies. |
| OS4 | **Vega added** (`modelGreeks.vega`), through a `greeks` parameter of `Recorder` and `ChainSnapshot`. The probe's default fields stay as they were, so its JSON doesn't change. "Complete" (when a batch may end early) still needs OI, IV, gamma, bid and ask, not vega. | The asked-for field, with no change to the probe. | Add vega for both (changes the probe's output). |
| OS5 | **The store is its own SQLite file**, `/data/options.sqlite`, in its own volume. It has three tables (`option_runs`, `option_quotes`, `underlying_quotes`) and a view `ok_option_quotes`, with numbered migrations as in the datafeed store. It uses the rollback journal, not WAL: one daily writer, and nothing reads during the write. Values are stored as received (IBKR's −1 "no bid" stays −1; NULL means no value arrived). Each value's first and last time is kept in `field_times` (JSON), plus first and last tick per contract. | No writer contention with the recorder, no dependency on the stream profile, and a self-contained file to back up. | A table in `datafeed.sqlite` (shared writer; that file exists only with the stream profile). |
| OS6 | **Underlying:** `under_con_id` is each contract's `underConId`, as in the probe; that one gets quoted. `chain_under_con_id` is the underlying whose option chain listed the expiry (when there is exactly one). Both conIds are stored, and every chain → expiry mapping is in `option_runs.expiry_sources`. In attempt 3 the two always agreed. | Stores what the owner named, and keeps the probe's choice for F. | Quote the chain's underlying instead. |
| OS7 | **Every invocation is one `option_runs` row:** `ok`, `skipped` (closed, holiday, 10197, or the day already has an ok run) or `failed`, with `reason`. A partial unique index allows one ok run per trade date. A second run on the same trade date requests nothing. Error 10197 → `skipped`, exit 4. The holiday calendar running out (2028) → `failed`, exit 1, so it alerts. Data from a run that stopped part-way is never stored. | An auditable day-by-day record; no duplicate snapshots; no partial day mistaken for a full one. | Store partial data; skip silently when the calendar ends. |
| OS8 | **No retries anywhere.** Host cron runs `run_snapshot.sh` once, weekdays 05:00 UTC. Exit 4 sends one Telegram notice saying how to run it by hand; other failures send one message; exit 3 is only logged. `flock` stops a second copy from starting. The compose service has a profile and no restart policy, so neither `up` nor Docker ever runs it again. | Matches "never retried in a loop"; a human decides about a rerun. | A long-running scheduler container (`restart:` would re-run it after a crash). |
| OS9 | **Its own compose project, image and checkout** (`oparli-options`, `oparli-options:local`, `~/oparli-options` as a git worktree on the host). It joins the scanner project's network as an external network (`scanner_scannernet`, which c62810d and `main` both create) to reach `ibgateway`. Nothing in `deploy/scanner/` changes. | The scanner is on hold: deploying this rebuilds no scanner image and switches no scanner checkout. It works before or after the cut-over. | A service in `deploy/scanner/docker-compose.yml` (shared image, so a deploy touches the scanner). |
| OS10 | **Backups: its own `deploy/options/backup.sh`**, run after every ok snapshot. It uses `backup_sqlite.py` (the online backup API, integrity check, expects `option_runs`) inside a one-off options container, then gzip, then S3 with SSE under the same `BACKUP_S3_URI`, prefix `options/`. The host's IAM policy (`oparli/*`) already covers it. No lifecycle rule covers `options/`, so copies are kept until the owner adds the 30-day rule in the README (optional). | It works on the host as it is (c62810d's `backup.sh` may predate the store), and data that can't be re-fetched is backed up the same morning. | A section in `deploy/scanner/backup.sh` (needs the cut-over, and scanner-side files). |
| OS11 | **Client id 62.** The probe is 61, and 1, 2, 11, 21, 31, 43, 44, 97, 98, 996 and 999 are taken or reserved (GF2). It can be overridden with `OPTIONS_IB_CLIENT_ID`. | No collision, even with the probe running at the same time. | Reuse 61. |
| OS12 | **The fake IBKR client is the study's `research/gex_feasibility/fake_ib.py`**, loaded by path. It lists GC months consecutively (V6 … J7), with OG chains on Z6, G7 and J7 only (GF19). The tests use 10 strikes (60 options + 2 futures), so there is more than one batch of 50. The shell scripts are tested with stub `docker`, `flock`, `curl`, `aws` and `hostname`. No test touches the network. | One fake, which already reproduced attempt 1's failure. | A second fake in `tests/options/` (two to keep in step). |
| OS13 | **Not verified here:** the Docker build and a real gateway run. Docker isn't installed on this machine, and EC2 is off limits. Python 3.12 (the image's version) isn't installed either. The code is checked with ruff `--target-version py312`, and the tests ran on 3.13. The first real run is step 4 of the README, by the owner. | Says what wasn't run. | none |
| OS14 | **The cron line is in host time**, and the README's step 0 checks that it's UTC. Debian's cron has no reliable `CRON_TZ`. Whatever time it fires, the snapshot checks COMEX hours itself. | No silent hour shift. | `CRON_TZ=UTC` in the crontab. |
